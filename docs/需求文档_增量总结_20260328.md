# 需求文档：Agent 增量总结（按步合并 + SSE 实时覆盖）

## 1. 文档目标

定义「增量总结」能力：在 ReAct 执行过程中，**每完成一步工具执行并得到 observation 后**，将**本步结果**与**当前已有的运行总结合并**，调用大模型生成**新的全局总结**；新总结**覆盖**旧总结，并通过 **SSE 流式**推送给前端，直至本轮任务所有步骤结束。

**本能力要解决的两个核心问题（相对「只在最后做一次总结」）：**

1. **总结时间（等待与单次负担）**：末尾一次性总结往往要在**全部 observation 累积**后再调用模型，输入长、输出长，用户**等待久**、**阅读成本高**。增量总结把合并工作**按步分摊**，每一步只做「旧总结 + 本步 observation」的**小规模更新**，用户**更早**看到阶段性结论，且可**削弱**终局再生成一篇超长文的必要性（见第 5.4 节）。
2. **结论形态（清单优于长文）**：末尾长文不易扫读与对照执行。增量总结要求输出**结构化清单**（要点、状态、待办、风险等，见第 4.2 节），让用户在任务进行中就能**持续获得可执行的条目化总览**，而不是最后才面对一大段叙述。

本文档作为后端引擎、SSE 协议与前端展示的改造依据，可与现有 `step` 内事件、`summary_stream` 等机制对齐演进。

---

## 2. 背景与现状

### 2.1 用户痛点

- **末尾总结太长、太晚**：整轮结束后才生成总结，模型侧往往要消化**全量上下文**，产出篇幅大，用户**等待时间长**，且**不易快速抓住重点**。
- **缺少「可执行的聚合视图」**：单步 `observation` 分散，缺少**跨步骤、持续更新**的**清单式**总览（已确认事实、待办、建议下一步等），难以对照执行。

### 2.2 现状（与本文档相关的部分）

- ReAct 主循环按步产出 `observation` 等事件；引擎内已有 `summary_stream` 等流式车道（如纯对话、部分总结场景）。
- 最终类总结多集中在**流程末尾**（例如 `done` / findings / unified final summary 等路径），**不是**每步 observation 之后都刷新一份「全局运行总结」。

---

## 3. 范围

### 3.1 纳入范围

- **触发时机**：每步工具执行完成且 observation（或其等价、已落定的「本步结果」文本）可用之后。
- **合并输入**：
  - **上一版运行总结**（首轮可为空或固定占位，如「尚无」）。
  - **本步结构化或文本化结果**：至少包含步骤标识（序号/工具名/简要意图）、observation 正文（或经截断/脱敏后的摘要输入）。
- **生成方式**：调用大模型，**显式指令**为「在保留旧总结有效信息的前提下，融入本步新事实，输出新的完整总结」（非简单字符串拼接）；并**强制偏清单化**（见 4.2），以优化扫读与执行。
- **输出形态**：**单次总结一次完整覆盖**——新总结文本替换内存中的「当前运行总结」；通过 SSE **增量字符/分块**推送（与现有流式总结体验一致），前端以**同一块 UI 区域**展示，**每次新一轮总结开始时可清空再打字**或采用「版本号 + 全量替换」策略（见第 6 节）。
- **终止条件**：本轮 ReAct 所有步骤结束（与现有 `finished` / `done` 语义对齐）；最后一步若仍触发增量总结，**可与**现有「最终总结」**合并设计**或**去重**（见第 5.4 节）。

### 3.2 不纳入范围（可单列后续需求）

- 对历史会话的离线重算总结（本文仅针对**单次流式请求生命周期**内）。
- 多用户协作编辑同一份总结。
- 非 ReAct 链路的统一改造（除非产品明确要求）。

## 4. 功能需求

### 4.1 核心流程（逻辑顺序）

1. 初始化：`current_running_summary = ""`（或 null），`summary_version = 0`（建议用于前端去重/重绘）。
2. 第 *i* 步 observation 就绪后：
   - 组装 prompt：`f( current_running_summary, step_meta_i, observation_i, locale )`。
   - 调用 LLM **流式**生成 `new_summary`。
   - 流式过程中通过 SSE 下发增量（见 4.3）。
   - 流结束后：`current_running_summary = new_summary`，`summary_version += 1`。
3. 第 *i+1* 步重复步骤 2。
4. 全部步骤结束后：默认**直接使用最后一次增量总结**作为对外主结论；仅在选用 5.4 方案 B 或产品明确要求时，再增加短「终局润色」或独立终局报告（见 5.4）。

### 4.2 总结内容约束（建议写入系统/用户提示）

- **连贯性**：新总结必须是**完整可读**的一篇，不得仅输出「新增补丁句」要求前端拼接（避免前端逻辑复杂与重复）。
- **清单化 + 固定 Markdown 标题（必须）**：增量总结正文须使用**二级标题**（`## …`）划分区块，标题文案**与 locale 绑定且固定不可改字**（便于前端按标题解析、锚点跳转或样式高亮）。区块顺序固定如下：
  - **简体中文（`zh-CN` 等）**  
    - `## 已确认`：当前已核实的事实、结论或证据要点；  
    - `## 待办与建议下一步`：仍需执行或验证的事项；  
    - `## 风险与阻塞`：失败步骤、缺失信息、需用户决策的点。  
  - **英文（`en`）**  
    - `## Confirmed`  
    - `## Next steps`  
    - `## Risks and blockers`  
  每个二级标题下使用 **Markdown 无序列表**（`-`）罗列条目；**禁止省略标题行**：若某区块当前无内容，在该标题下写单独一条 `- 无。`（英文：`- None.`）。除可在**全文最前**增加不超过两句总起外，**禁止**用其它任意 `##` 标题，避免前端解析分叉。  
  **其它 locale**：须在 `locale_prompts` 中增补与上表**语义等价**的三段固定 `##` 文案，并纳入验收（与 zh-CN / en 同一套规则）。
- **忠实性**：以 observation 与旧总结为据，不编造未出现的结论；若本步无有效信息，可明确写「本步无新增有效结论」并保留旧要点。
- **长度**：可配置最大字数或 token 上限；**单次增量输出宜短于**「终局一次性长文总结」——以**信息密度与清单条数**为优先，而非篇幅。超长时对**输入**侧先做裁剪（旧总结滑动窗口 / 本步 observation 截断），而非无限增长 prompt。
- **语言**：与用户 `locale` 一致（与现有 Agent 行为一致）。

### 4.3 SSE 与协议（需求级，非实现定稿）

- **必须**：每次增量总结有一次**可关联的版本标识**（如 `summary_version` 或 `incremental_summary_id`），便于前端在重连、乱序时丢弃过期块。
- **必须**：支持**流式增量**（delta），结束时发送**明确结束事件**（如 `incremental_summary_done` 或与现有 `summary_stream` 结束约定一致）。
- **建议**：新增独立事件名（例如 `running_summary_stream` / `incremental_summary_delta`），与单步 `observe` 内 UI 总结、最终 `done` 附带的 findings 区分，避免前端混用。
- **建议**：载荷字段至少包含：`version`、`delta`（可选 `full_text` 仅在非流式降级时使用）。

### 4.4 前端展示

- 专用区域展示「**运行中总结**」，每次新版本到达时：
  - **方案 A**：清空后从空开始流式展示（简单，视觉上有「刷新」感）。
  - **方案 B**：静默替换为新版全文再流式（若实现成本高可阶段二）。
- 展示上对正文做 **Markdown 渲染**，并**可依赖上述固定 `##` 标题**做样式区分（如折叠块、色条）；保证列表层级在窄屏下仍可扫读。
- 与步骤时间线、单步 observation 卡片**并存**：运行总结是**条目化聚合视图**，不替代单步明细。

### 4.5 持久化（可选）

- 若 AI 消息落库需展示历史：每次 `incremental_summary_done` 可将**最终一版**写入消息 JSON 的固定字段（如 `running_summary_final`），避免把每一次中间版本都存满库表（可配置）。

## 5. 非功能需求与边界

### 5.1 性能与成本

- **时间体验上的设计意图**：相对「最后一次性总结」，增量模式将单次推理的**输入规模**控制在「当前总结合本步 observation」量级，通常比终局全量汇总**更短、更可预测**；用户**不必等到全部结束**才有总览，从体验上**优化总结可感知等待时间**。（总调用次数增加，需在成本与体验间用开关/降频平衡。）
- 每步多一次 LLM 调用，需支持**开关**（如 `INCREMENTAL_SUMMARY_ENABLED`）与**采样**（如每 N 步才总结一次，作为降级，可选）。
- 应对**慢模型**：不阻塞工具循环的硬性路径——总结生成应与主循环**异步协调**（可排队），但需定义：若下一步 observation 已到达而上一轮总结尚未结束，是**取消上一轮**、**跳过本轮**还是**串行队列**（建议：**串行队列** + 版本号丢弃过期结果）。

### 5.2 可靠性与错误处理

- LLM 失败：保留 `current_running_summary` 不变；SSE 下发可选 `incremental_summary_error`（含 `version`）；本步仍正常继续。
- 超时：可返回部分文本并标记 `truncated` 或直接使用旧总结（产品选择）。

### 5.3 并发与 DAG（若存在多步并行）

- 若未来存在**并行多步**同时结束：需定义**合并单元**——按「逻辑步完成事件」串行触发，或「一批 observation 合并为一次增量总结」（本文默认**每步一次**；并行场景需单独补充规则）。

### 5.4 与「最终总结」的关系

- **推荐默认（与「末尾总结太长」对齐）**：**方案 A** —— 以**最后一次增量总结**作为对外主结论；`done` / findings **不再**重复跑一篇超长总结，最多**极短收尾**（如一句状态、链接或引用已有清单），避免用户再读第二份长文。
- **方案 B**（非默认）：保留现有终局长文；增量总结仅作过程态。仅当合规/审计**必须**独立终局报告时选用，并需在 UI 上区分「过程清单」与「终局报告」，避免信息重复、篇幅翻倍。

## 6. 验收标准（建议）

1. 开启功能后，**至少每一步 observation 之后**，前端「运行中总结」区域会收到**一轮**新的流式内容，且**内容与之前版本不同**时体现本步新信息。
2. 各版总结**必须**出现与 locale 一致的三个固定 `##` 标题（见 4.2），其下为列表条目；无内容时该区块为 `- 无。` / `- None.`；用户能在任务中途**扫读**三块内容，而非仅长段落叙述。
3. 相对仅末尾总结：用户**更早**首次看到全局向总结（不晚于第一步 observation 后的约定时限内）；终局若采用 5.4 方案 A，**不应**再出现与增量清单重复的**第二篇超长总结**。
4. `summary_version`（或等价字段）**单调递增**；乱序或过期 delta 不应覆盖较新版本。
5. 关闭功能后，行为与线上一致（仅末尾总结或无此区域）。
6. LLM 失败时**不阻塞**主流程，且前端可感知失败或静默保持旧文（与产品选定策略一致）。

- Prompt：`agents/prompts.py`（或 `locale_prompts`）新增「增量合并总结」模板，**原文收录** 4.2 节所列固定 `##` 标题字符串，并在系统提示中要求模型严格遵守。

## 8. 开放问题（待产品/技术评审）

1. 输入给 LLM 的 observation 是**全文**还是**已由本步 observe 模型压缩过的 summary_nl**？（影响 token 与忠实度。）
2. 并行步骤时的触发策略（见 5.3）。
3. 终局与增量总结是否二选一或并存（见 5.4）。
4. 是否需要用户设置「总结详略」（短/中/长）。

## 9. 关联与可顺带完成的任务清单

以下为落地增量总结时，**常与主需求一并规划**的任务，可按优先级勾选；未勾选也不影响理解本文核心流程。

- [ ] **协议与文档**：在现有 SSE / 双通道对照文档中补充增量总结事件名、字段、`version` 与结束边界，避免前后端各写一套。
- [ ] **功能开关与配置**：环境变量或项目级配置（开关、每 N 步触发、最大输入长度、模型路由是否与主对话一致）。
- [ ] **Prompt 与多语言**：`prompts` / `locale_prompts` 中独立模板；**固定 `##` 标题**中英文案与 4.2 完全一致；失败/空 observation 的固定话术与「不编造」约束。
- [ ] **队列与取消策略**：主循环与总结任务异步时，明确串行队列、超时、下一步到达时是否丢弃未完成的旧总结流。
- [ ] **观测与排障**：`request_id` / `session_id` / `step_id` 与 `summary_version` 打日志；可选 metrics（每步耗时、token、失败率）。
- [ ] **单测与回放**：SSE 片段 golden / reducer 单测；模拟「乱序 delta」「重复 version」时前端不覆盖新版本。
- [ ] **前端状态机**：composable 中统一消费 `delta` + `done` + `error`；与重连、会话切换时的清理与恢复。
- [ ] **UI/UX**：运行中总结区域占位、加载态、流式打字与「整轮结束」后的终局文案衔接；移动端或窄屏折叠策略。
- [ ] **持久化与历史**：会话落库是否只存最终一版、是否需在详情页回放最后一次运行总结；与现有 AI 消息 JSON 字段对齐。
- [ ] **权限与脱敏**：observation 进总结前是否走与工具结果一致的脱敏/截断；敏感项目是否强制关闭增量总结。
- [ ] **成本与限流**：按用户/项目配额、并发请求上限；必要时降级为仅末尾总结。
- [ ] **与终局总结对齐**：按第 5.4 节选定方案后，改 `done` / findings 文案或去重逻辑，避免用户看到两份矛盾长文。
