# 卡片设计与界面优化需求文档

## 1. 需求背景

当前BadCase Doctor系统中，迭代计划部分存在多种类型的计划（如bug类型、badcase类型、测试用例类型），导致管理复杂且不够灵活。为了提高系统的可扩展性和用户体验，参考百度iCafe的设计理念，引入卡片抽象层，统一管理不同类型的工作项。

## 2. 设计目标

- 引入卡片抽象层，统一管理不同类型的工作项
- 简化迭代计划管理，不再区分计划类型
- 优化界面布局，提升用户体验
- 支持插件机制，为未来功能扩展预留空间
- 改进搜索功能，实现全局搜索

## 3. 核心设计

### 3.1 卡片抽象

- **卡片定义**：卡片是系统中最小的工作项单位，包含标题、类型、状态、负责人等基本属性
- **卡片类型**：支持以下类型
  - Bug：缺陷报告
  - BadCase：异常用例
  - TestCase：测试用例
- **卡片属性**：保持与原有系统的bug、badcase列表界面一致，包括但不限于：
  - 标题
  - 类型
  - 状态
  - 负责人
  - 创建时间
  - 操作按钮
- **卡片状态**：每个类型的卡片保持原有系统的状态流转逻辑

### 3.2 迭代计划管理

- **计划结构**：迭代计划不再区分类型，所有类型的卡片都可以添加到同一个计划中
- **未计划卡片**：统一管理所有未分配到计划的卡片，不再按类型分类
- **卡片关联**：卡片可以在不同计划之间移动

### 3.3 界面布局

#### 3.3.1 左侧导航栏

- **窄条导航**：在当前红框位置提供一个窄条的竖着一栏，包含：
  - 文件夹图标：点击返回迭代计划展示左侧部分
  - 搜索按钮：点击打开全局搜索功能
  - 插件机制占位：为未来插件功能预留入口

#### 3.3.2 主内容区

- **未计划卡片视图**：参考iCafe设计，展示所有未计划的卡片
- **计划卡片视图**：展示当前计划中的所有卡片
- **卡片创建界面**：参考iCafe设计，提供快速创建卡片的界面，并且挂在tab上，确保切换到别的界面时对话面板操作不会丢失
- **卡片详情界面**：打开卡片（如Bug详情）时，保持在tab上显示，与原有系统保持一致，不允许切换界面
- **卡片管理界面**：所有卡片相关的管理功能（如编辑、删除、状态变更等）都挂在tab上，确保操作的连续性和一致性

### 3.4 搜索功能

- **全局搜索**：将原搜索框功能迁移到专门的搜索模块
- **搜索范围**：支持搜索所有类型卡片的标题、描述等内容
- **搜索结果**：点击搜索结果可直接跳转到对应卡片详情

### 3.5 卡片创建流程

1. 用户点击"新建卡片"按钮
2. 弹出卡片类型选择界面（参考iCafe设计）
3. 用户选择卡片类型（Bug、BadCase、TestCase）
4. 填写卡片标题等基本信息
5. 点击"确定"按钮，进入对应类型的详细编辑界面
6. 完成详细信息填写后，卡片创建完成

## 4. 功能实现

### 4.1 前端实现

- **组件设计**：
  - 将卡片相关功能拆分为独立组件，在`ProjectDetail.vue`中引用这些组件，避免主组件过于臃肿
  - 新增`CardList.vue`：卡片列表组件，负责展示卡片列表
  - 新增`CardCreate.vue`：卡片创建组件，负责卡片的快速创建
  - 新增`CardDetail.vue`：卡片详情组件，负责展示和编辑卡片详情
  - 新增`CardTypeSelector.vue`：卡片类型选择组件，负责选择卡片类型
  - 重构左侧导航栏，添加窄条导航
  - 实现全局搜索功能

- **状态管理**：
  - 使用Vue的响应式数据管理卡片状态
  - 实现卡片在计划之间的移动
  - 同步更新相关视图

### 4.2 后端实现

- **API接口**：
  - 新增卡片相关接口：创建、查询、更新、删除卡片
  - 新增卡片类型管理接口
  - 新增卡片与计划关联接口

- **数据库设计**：
  - 新增`cards`表，存储卡片基本信息
  - 新增`card_types`表，存储卡片类型定义
  - 新增`card_plan_relations`表，存储卡片与计划的关联关系

### 4.3 插件机制

- **插件系统设计**：
  - 定义插件接口规范
  - 实现插件加载机制
  - 为插件预留UI入口

- **预留功能**：
  - 卡片类型扩展
  - 卡片状态自定义
  - 卡片字段自定义

## 5. 集成与兼容性

### 5.1 现有功能集成

- **Agent集成**：更新Agent相关代码，支持新的卡片抽象
- **跳转高亮**：同步修改跳转和高亮定位功能，确保与新的卡片结构兼容
- **基线功能**：确保基线功能与卡片抽象兼容

### 5.2 数据迁移

- **现有数据迁移**：将现有的Bug、BadCase、TestCase数据迁移到新的卡片结构
- **计划数据迁移**：将现有的计划数据与卡片关联

## 6. 用户体验优化

- **操作流程优化**：简化卡片创建和管理流程
- **视觉设计**：参考iCafe的视觉风格，提升界面美观度
- **界面适配**：确保在桌面端不同屏幕尺寸上的良好体验
- **加载性能**：优化数据加载和渲染性能

## 7. 测试计划

- **功能测试**：测试卡片创建、编辑、删除等基本功能
- **集成测试**：测试与现有功能的集成
- **用户测试**：邀请用户进行体验测试，收集反馈
- **性能测试**：测试系统在大量卡片情况下的性能

## 8. 实施计划

1. **需求分析与设计**：完成详细设计文档
2. **前端实现**：实现卡片抽象和界面优化
3. **后端实现**：实现卡片相关API和数据库设计
4. **数据迁移**：将现有数据迁移到新结构
5. **测试与优化**：进行全面测试和性能优化
6. **上线部署**：发布新功能

## 9. 风险评估

- **数据迁移风险**：需要确保现有数据的完整性和一致性
- **兼容性风险**：需要确保与现有功能的兼容性
- **性能风险**：需要确保在大量卡片情况下的系统性能
- **用户适应风险**：用户需要时间适应新的界面和操作流程

## 10. 结论

通过引入卡片抽象层和优化界面设计，BadCase Doctor系统将变得更加灵活、可扩展和用户友好。参考iCafe的设计理念，结合AI测试的特点，打造一个更加专业、高效的测试管理工具。
