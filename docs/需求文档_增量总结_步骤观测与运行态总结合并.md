# 需求文档：增量总结（步骤观测与运行态总结合并）

## 1. 文档目标

定义「运行态增量总结」能力：在 Agent 多步执行过程中，**每完成一步**即将该步的 **observation（工具/执行结果）** 与**当前已有的全局总结**合并，经大模型生成**新的全局总结**；新总结**覆盖**旧总结，并通过 **SSE** 实时推送给前端；循环直至本轮任务所有步骤结束。

本文档作为产品/研发对齐依据，便于与现有 ReAct 流式协议、会话落库方案衔接。

---

## 2. 范围

### 2.1 纳入范围

- 后端：在单轮 Agent 请求（如 `POST /api/agent/react` 流式）生命周期内，维护**会话级运行态总结**文本（或等价结构化载体），并在每步 observation 就绪后触发一次「合并 + LLM 重写」。
- 传输：通过现有或扩展的 **SSE** 事件，将**每次更新后的完整总结**或**可拼接的增量**送达前端（见第 5 节协议建议）。
- 前端：在聊天/任务面板中展示「截至目前为止的结论」，随 SSE 更新而刷新，无需等到整轮 `done` 才看到总结。

### 2.2 不纳入范围（可另起需求）

- 跨多轮用户消息的「项目级长期记忆总结」（与单次 react 会话内增量总结不同）。
- 纯离线批处理、非流式 HTTP 一次性返回的总结接口（若需可复用同一合并逻辑）。
- 对 observation 原文做永久全量存档的合规/审计策略（仅在本需求中假设已有或可配置）。

---

## 3. 背景与现状

### 3.1 用户痛点

当前体验上，**面向用户的全局结论**往往在**最后一次**才完整呈现（例如仅在流程末尾的 `done`/最终 summary 阶段）。长任务中用户长时间看不到「到目前为止已经确定了什么」，感知为黑盒。

### 3.2 与现有能力的关系（概念对齐）

- 项目中已存在按步骤的 **observation**、以及多种 **summary** 相关能力（如步骤内 observe 总结、最终 unified summary 等）。本需求强调的是：**跨步骤、可累积、可覆盖**的**单一运行态「总览总结」**，且**逐步刷新**并 **SSE 下发**。
- 实现落点预期涉及：`agents/react_simplified.py`（或等价 ReAct 引擎）中「每步 observation 完成」的锚点，以及 `routers/agent.py` 的 SSE 封装；前端在消费 `step` / 顶层事件处增加对「运行态总结」的订阅与展示。

---

## 4. 目标能力（一句话）

> **每步 observation 到达 → 与当前总结合并 → LLM 生成新总结 → 覆盖旧总结 → SSE 推送 → 重复至全部步骤结束。**

---

## 5. 功能需求

### 5.1 触发时机

1. **主触发**：某 **ReAct 步骤**执行结束，**observation** 已确定（含：工具返回结构化结果、错误信息、或经截断/脱敏后的可下发文本，具体以现有引擎约定为准）。
2. **不触发**（建议默认，可配置例外）：
   - 纯内部元步骤（若有）、或 observation 为空且明确标记为「无实质输出」的步骤（需定义规则，避免无意义调用 LLM）。
   - 用户已取消/会话已终止后的迟达事件（应丢弃或只落日志）。

### 5.2 输入构成（合并上下文）

每次调用总结 LLM 时，建议至少包含：

| 输入块 | 说明 |
|--------|------|
| 已有运行态总结 | 上一步结束后的总结全文；第一步可为空模板或固定引导语。 |
| 本步 observation | 本步权威结果文本（或 JSON 序列化 + 长度上限）；需与 UI/日志一致的版本。 |
| 步骤元信息（可选） | 步骤序号、工具名、计划项 id 等，便于总结中引用「第 N 步」。 |
| 用户原始目标（可选） | 本轮用户诉求摘要，防止总结偏离任务目标。 |

**合并策略**：产品语义为「在**不丢失**已确认结论的前提下，**吸收**本步新信息」。实现上由 **LLM 提示词**约束：输出即为**新的完整总结**（见 5.3），而不是要求前端自行拼接多段。

### 5.3 输出与覆盖规则

1. **输出物**：一段（或多段结构化字段，但用户可见主字段为）**完整的新总结**，代表「截至当前步骤」的全局视图。
2. **覆盖规则**：新总结**替换**内存中的运行态总结；前端展示以**最近一次 SSE 有效载荷**为准。
3. **一致性**：同一请求 `request_id` / `session` 内，总结版本建议带单调递增 **`summary_revision`**（或时间戳），便于前端去重与调试。

### 5.4 流式行为

1. **LLM 生成**：总结生成可采用**流式**（推荐，与现有 `summary_stream` 类事件一致）或**非流式**一次性下发。
2. **SSE 推送**：
   - 若流式：按 chunk 推送，**首包**或元数据中携带 `summary_revision`；**最后一包**标记完成，前端将缓冲区内容**原子替换**为当前版本全文（避免半句展示闪烁的策略见 5.5）。
   - 若非流式：单条事件携带完整新总结。

### 5.5 前端展示（体验）

1. 在任务进行过程中，展示区域标题建议为「当前进展」或「阶段性结论」（文案可 i18n）。
2. **流式总结**：可选策略——（a）流式打字机更新；（b）生成中显示 loading，完成后一次性替换（实现简单、闪烁少）。需求上不强制，由前端与性能权衡。
3. **步骤回放/历史**：若用户展开历史步骤，**运行态总结**仍表示「当前最新全局视图」，与单步 observation 列表并存，语义不混淆。

### 5.6 结束边界

1. 当本轮 **所有步骤结束**（与现有 `finished` / `done` 语义对齐）时，**最后一次**增量总结应已反映全部 observation。
2. 若最终阶段仍有「终局 unified summary」逻辑，需明确二者关系（见第 7 节待定项）：二选一、或终局总结在运行态总结基础上微调用、或终局仅补充固定收尾句。

---

## 6. 非功能需求

### 6.1 性能与配额

1. **调用频率**：每步最多 1 次总结 LLM（若一步内多次 observation 碎片，应先在本步内合并为单一 observation 再触发，避免爆炸调用）。
2. **Token 控制**：对 observation 与「已有总结」设**上限**（字符数或 token 估算），超限截断策略需在实现中写明（尾部截断 / 保留关键字段）。
3. **并发**：新一步到达时，若上一总结 LLM 仍在生成，策略需定义（建议：**取消**未完成的旧总结生成任务，或以**队列**保证同一 session 内串行、只保留最新 revision 的结果）。

### 6.2 可靠性与降级

1. LLM 超时/失败：保留**上一份**有效总结，本步可打标「本步总结失败」的轻量提示事件（可选）；不应阻塞主 ReAct 循环继续执行（除非产品明确要求强一致阻塞）。
2. 后端重启/断连：运行态总结以**客户端已收 SSE** 为准；持久化是否写入消息体见第 7 节。

### 6.3 安全与隐私

1. observation 进入总结前，沿用现有**脱敏/截断**规则（若有）。
2. 日志中打印总结全文需受日志级别或开关控制。

---

## 7. 协议与数据契约（建议）

以下为建议字段，实施时可与现有 `type=step` / 顶层事件统一命名空间。

**事件名（示例）**：`running_summary_delta` + `running_summary_done`，或复用现有 `summary_stream` 并增加 `scope: "running"`、`revision` 区分终局总结。

**建议载荷字段**：

- `revision`：整数，单调递增。
- `step_index`：触发本总结的步骤序号。
- `delta`：（可选）本包文本增量。
- `text`：（可选）完整文本，用于非流式或 done 包。
- `done`：布尔，表示本 revision 生成结束。

前端以 `(revision, done)` 判定一次完整更新周期。

---

## 8. 验收标准

1. 多步任务执行中，**每步 observation 完成后**，前端能在**不刷新页面**的情况下收到 SSE，且展示的「运行态总结」内容**包含**此前步骤已确认信息，并**融入**本步新信息。
2. 任意时刻界面仅保留**一份**当前权威运行态总结（与 revision 一致），新 revision 到达后**覆盖**旧内容。
3. 整轮结束后，最终运行态总结与**所有步骤 observation** 在人工抽检下**无明显矛盾**（允许精简表述，不允许编造未出现的结论）。
4. 在 LLM 失败或跳过时，主任务仍可完成，且系统行为符合 6.2 约定。

---

## 9. 待定项与风险

| 项 | 说明 |
|----|------|
| 与终局 summary 关系 | 是否保留独立「最终润色」、如何避免用户看到两次大块文本突变。 |
| 持久化 | 是否将每次 revision 或仅最终版写入 `chat-sessions` 消息，影响复盘与刷新恢复。 |
| 多工具并行步 | 若一步内并行多个 observation，合并触发点与 revision 计数需单独定义。 |
| 成本 | 步数多时 LLM 调用次数线性增长，可能需要「每 K 步合并」或「仅关键工具触发」的可配置策略。 |
