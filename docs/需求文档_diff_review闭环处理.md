# 需求文档：Diff Review 闭环处理

## 1. 背景与问题

当前对话驱动修改（列表字段 + 详情字段）在多轮会话中会出现如下问题：

- 同一条记录多次修改后，Diff 展示可能不一致，用户难以判断“当前待采纳的是哪一版”。
- 已采纳后的 Diff 仍可能在列表/详情残留，造成“看起来还没处理完”。
- 后续再次修改同一记录时，缺少明确的新旧边界，闭环不清晰。

目标是建立一个可验证的闭环：  
**生成 Diff -> 查看 Diff -> 采纳/拒绝 -> 清理展示 -> 再次修改时重新生成新 Diff。**

---

## 2. 术语定义

- `记录`：BadCase / Bug / TestCase 中某一条具体数据（由 `target + target_id` 唯一标识）。
- `Diff Review`：某次对话生成的待确认变更集合（字段 old/new 与可视化 diff）。
- `待采纳`：`confirmation_required = true` 且未执行采纳动作。
- `已采纳`：`confirmation_required = false`，并已应用到真实记录。
- `最新 Diff`：同一记录当前“尚未采纳”的最终合并结果。

---

## 3. 业务目标

对每个 `project_id + target + target_id`（**不按 ChatSession 分版**），系统在任意时刻只维护一份“最新且有效”的 Diff Review 语义：

1. **首次生成**：对话第一次修改该记录时，生成 Diff Review，列表与详情均可查看。
2. **未采纳再次修改**：如果还未采纳，后续对话（**含不同 ChatSession**）再次修改该记录，应合并并产出新的“最新 Diff”；**同一字段**只保留最新一次修改。
3. **采纳后无新改动**：若最新 Diff 已采纳，且没有新改动，则该 Diff 不再展示于列表/详情。
4. **采纳后再次修改**：后续若再改同一记录，应重新产生新 Diff Review（新一轮生命周期）。

---

## 4. 核心规则

### 4.1 生成规则（首次）

- 触发条件：对话返回 modify/create 的预览结果，且记录存在可变更字段。
- 结果：
  - 写入待确认数据（pending）。
  - 列表行可见 Diff（高亮/old->new）。
  - 详情页可见对应字段 Diff。

### 4.2 合并规则（未采纳期间多轮对话）

同一记录未采纳时，多次对话的 Diff 合并遵循：

- **不同字段**：并集保留。
- **相同字段**：后一次覆盖前一次的 `new` 值。
- `old` 值以本轮生命周期首个有效 old 为准（用于表达“从哪里改到哪里”）。

形成一个新的“最新 Diff Review”，并替换旧展示。

### 4.2.1 前后端合并职责（新增）

为避免前端多处合并导致口径不一致，合并以**后端统一计算结果**为准：

- 前端在“本次产生新 diff”的请求中，必须同时提交：
  1. 本次对话产生的 `new_diff/new_modifications`
  2. 该记录当前“未采纳”的 `pending_diff/pending_modifications`（若存在）
- 后端接收后执行统一合并（不同字段并集、相同字段后者覆盖），生成唯一 `merged_diff`。
- 后端返回 `merged_diff + merged_modifications + new_fingerprint + lifecycle_id`。
- 前端只负责展示后端返回结果，不再自行二次推导最终 diff。

> 结论：**旧未采纳 diff 也要发给后端**，由后端综合生成新的 diff。

### 4.2.2 新 Diff 推导定义（新增）

新 Diff 的生成必须遵循如下定义：

- **基于上一版未采纳 Diff（pending） + 当前对话新增修改（delta）推导**；
- 若不存在上一版 pending，则当前对话 delta 直接形成首版 Diff。

公式表达：

`merged_diff_t = merge(pending_diff_(t-1), delta_from_current_chat_t)`

其中：

- `pending_diff_(t-1)`：同一 `target + target_id` 上一版未采纳 Diff；
- `delta_from_current_chat_t`：当前对话产出的新增修改；
- `merge` 规则：
  - 不同字段取并集；
  - 相同字段使用当前对话的 `new` 覆盖上一版 `new`；
  - 字段 `old` 保持该生命周期首个有效 old（用于表达“起点到当前”的累计变化）。

实现约束：

- 推导过程由后端统一执行，前端不得自行最终合并；
- 前端仅提交 `pending + delta` 并展示后端返回的 `merged_diff`。

### 4.3 展示规则

- 列表和详情展示来源一致：都读取该记录的“最新有效 Diff”。
- 不允许列表与详情展示不同版本 Diff。
- 计划切换、Tab 关闭/激活时可以同步 pending 到列表，但**不得引发非用户意图的详情自动打开**。
- 历史消息中的“沙箱预览”卡片需要保留可追溯性：即使该条已采纳，也应保留只读预览入口（不可作为待确认项）。
- 已采纳项在聊天区可显示“已采纳/已处理”状态文案，但不得伪装为待确认 diff。

### 4.7 Tab 激活/新建规则（新增）

当用户点击沙箱预览（或 `grep` 导航跳转，或系统根据这两类导航执行跳转）时，若 Diff/目标记录所在上下文不在当前 Tab，必须按以下规则处理：

- 若 Diff 所在 `plan_id + 内容类型` 与当前计划列表 Tab 不一致：
  - **优先激活**已存在的目标计划列表 Tab；
  - 不存在则**新建**目标计划列表 Tab 并激活。
- 若 Diff 包含详情字段（需进入记录详情）：
  - **优先激活**已存在的该记录详情 Tab（`target + target_id`）；
  - 不存在则**新建**详情 Tab 并激活。
- 若当前处于某记录详情 Tab，但沙箱预览目标为另一个计划列表或另一条记录详情，不得复用错误 Tab；必须切换到“匹配目标语义”的 Tab。
- `grep` 导航与沙箱预览遵循完全一致的 Tab 规则：  
  - 命中目标是列表上下文时，激活/新建目标计划列表 Tab；  
  - 命中目标是详情上下文时，激活/新建目标详情 Tab；  
  - 禁止把 `grep` 命中结果渲染在当前不匹配的 Tab 中。
- “自动同步 pending 到列表”的链路只允许更新列表高亮与 pending 状态，不得循环触发重复 Tab 激活与重复加载。
- Tab 选择必须与 Diff 的实际归属一致，禁止把“测试用例计划的 Diff”渲染在“未计划 BadCase”Tab 中。
- 对“已采纳”的历史沙箱预览，点击卡片仍应执行导航（激活/新建目标 Tab），用于回看已修改记录。
- 但导航到目标 Tab 后，该记录不应再出现待确认 diff（不高亮 pending、不显示可采纳状态）。

Tab 身份建议：

- 计划列表 Tab：`plan-{plan_id}-{content_type}`（或等价唯一键）
- 详情 Tab：`detail-{target}-{target_id}`

同一身份键全局唯一：存在即激活，不存在才新建，避免重复 Tab。

### 4.4 采纳/拒绝规则

- **采纳成功**：
  - 清除该记录当前生命周期的 pending diff。
  - 列表不再显示该条 Diff 高亮。
  - 详情不再显示该条 Diff review。
- **拒绝成功**：
  - 同样清除 pending diff。
  - 不修改真实数据。

### 4.5 采纳后的再修改

- 若该记录后续再次被对话修改，视为新生命周期：
  - 新建 Diff Review；
  - 展示规则与首次生成一致。

### 4.6 跨对话相同 Diff 去重规则（新增）

当**不同对话**对同一记录生成的 Diff 语义完全一致时（字段集合一致，且每个字段 `old/new` 一致），按如下处理：

- 若当前存在该记录的未采纳 Diff：
  - 不新增新的 pending 项；
  - 复用现有最新 Diff（保持一次待确认入口）；
  - 可更新来源信息（如 `last_message_id`、`last_session_id`、`updated_at`）用于追踪。
- 若当前记录已采纳且无新改动：
  - 不应因“相同 Diff 再次出现”而重新展示待确认；
  - 仍保持“无 Diff 展示”状态。
- 仅当 Diff 语义发生变化（字段新增/删除，或任一字段 old/new 改变）时，才视为新的有效 Diff。

> 说明：这里比较的是“语义等价”，不是字符串等价。字段顺序、文案标签差异不应导致误判为新 Diff。

---

## 5. 状态机（单记录维度）

状态：

- `S0 无Diff`
- `S1 待采纳Diff`
- `S2 已采纳无Diff`

事件与迁移：

1. `S0 --(首次对话修改)-> S1`
2. `S1 --(未采纳再次修改)-> S1`（更新为新的最新 Diff）
3. `S1 --(采纳成功)-> S2`
4. `S1 --(拒绝成功)-> S0`
5. `S2 --(再次对话修改)-> S1`
6. `S2 --(无新改动)-> S2`（不展示旧 Diff）
7. `S1 --(跨对话相同Diff)-> S1`（复用当前 Diff，不新增待确认项）

---

## 6. 关键场景验收

### 场景 A：首次 Diff

1. 对话修改记录 A（列表字段/详情字段任意）。
2. 列表能看到 A 的 Diff。
3. 打开 A 详情，也能看到同一份 Diff。

### 场景 B：未采纳再次修改

1. 场景 A 后不采纳。
2. 再次对话修改 A（同字段或不同字段）。
3. 系统生成新的最新 Diff：
   - 不同字段被合并；
   - 相同字段以后者覆盖；
4. 列表与详情均展示新 Diff，而非旧 Diff。

### 场景 C：采纳后隐藏

1. 对最新 Diff 执行采纳。
2. 列表与详情都不再展示该 Diff。
3. 切换计划、关闭再打开 Tab 后仍不应复现旧 Diff。

### 场景 D：采纳后再次修改

1. 场景 C 后再次对话修改 A。
2. 生成新 Diff（新生命周期）。
3. 列表与详情可查看新 Diff，行为与场景 A 一致。

### 场景 E：不同对话生成相同 Diff（新增）

1. 会话 X 对记录 A 生成 Diff（未采纳）。
2. 会话 Y 再次产生与会话 X 完全相同的 Diff。
3. 系统不新增第二份 pending，不重复展示多份待确认；列表与详情仍只看到一份最新 Diff。
4. 若会话 X 的 Diff 已采纳，再出现相同 Diff 且无新改动，不应重新出现待确认。

### 场景 F：沙箱预览跨 Tab 跳转（新增）

1. 当前停留在“未计划 BadCase”列表 Tab。
2. 点击沙箱预览，目标记录属于某“测试用例计划”列表。
3. 系统应激活或新建该测试用例计划列表 Tab（而不是继续停留在未计划 Tab）。
4. 若预览包含详情字段，则应激活或新建该记录详情 Tab。

### 场景 G：目标 Tab 已存在时复用（新增）

1. 预先已打开目标计划列表 Tab 或目标详情 Tab。
2. 再次点击同目标沙箱预览。
3. 系统只激活现有 Tab，不新增重复 Tab。

### 场景 H：grep 导航跨 Tab 跳转（新增）

1. 当前停留在与命中记录不相关的 Tab（例如未计划 BadCase 列表）。
2. 在 `grep` 结果中点击某条命中记录（属于其他计划或某条详情）。
3. 系统按统一规则激活或新建目标 Tab（计划列表或详情），并定位到目标记录。
4. 若目标 Tab 已存在，仅激活不重复创建。

### 场景 I：已采纳历史沙箱预览可回看（新增）

1. 某条沙箱预览对应的 Diff 已采纳成功。
2. 回到历史消息区域，沙箱预览卡片仍可见（只读状态）。
3. 点击该卡片，系统应激活/新建对应的列表 Tab 或详情 Tab。
4. 跳转后断言：该记录不显示待确认 Diff（无 pending 高亮、无可采纳提示）。

---

## 7. 数据一致性要求

- 同一记录在任一时刻只允许一个“最新未采纳 Diff”语义。
- 采纳/拒绝后必须清理内存态与持久化态中的待确认标记。
- 视图恢复（刷新、切计划、切 Tab）时，展示必须可由状态重建，不能依赖偶然缓存。
- 跨会话相同 Diff 必须幂等：重复输入不产生重复待确认项。

---

## 8. 持久化与刷新一致性（新增，强约束）

### 8.1 持久化原则

Diff Review 不允许仅存于前端内存。以下状态必须落库（或持久化到可恢复存储）：

- `pending`（待采纳）
- `adopted`（已采纳）
- `rejected`（已拒绝）
- `superseded`（被新版本覆盖，不再有效）

最小建议字段（按记录维度）：

- `target`, `target_id`
- `lifecycle_id`（同一记录一轮 diff 生命周期标识）
- `diff_fingerprint`（规范化后 hash，用于幂等）
- `status`（pending/adopted/rejected/superseded）
- `diff_payload`、`modifications_payload`
- `created_at`, `updated_at`
- `source_session_id`, `source_message_id`
- `adopted_at/rejected_at`（可选）

### 8.2 刷新恢复规则

页面刷新、重开会话、重新进入项目时：

- 仅加载 `status = pending` 且为“当前有效版本”的 Diff；
- `adopted/rejected/superseded` 不得进入待确认展示集合；
- 前端 `pendingModifications`、Tab 本地缓存（`bcd:ss` / `pendingModifyDiff`）等必须以 **L0（`diff_review_state` + Chat Session 消息）** 为准重建，而不是反向覆盖数据库状态。
- Tab 恢复时同样遵循上述约束：即使历史上打开过某详情 Tab，若该记录 Diff 已 `adopted/rejected/superseded` 且无新改动，恢复后不得再显示旧 Diff。

### 8.3 采纳后的不可复现约束（你当前问题的核心）

当某条 Diff 已采纳后：

1. 持久化状态必须从 `pending` 原子切换为 `adopted`；
2. 前端本地缓存（内存 + 浏览器 `bcd:ss`，**非** 后端 Chat Session）必须同步清理；
3. 刷新后若无新改动，绝不允许再次出现这条 Diff；
4. 若再次出现，只能是“新生命周期 + 新 fingerprint”的新 Diff。
5. “历史沙箱预览卡片”允许保留为只读回看入口，但其状态必须与 `adopted` 一致，且不得重新进入待确认集合。

### 8.4 原子性与并发

采纳操作应保证原子性（建议事务）：

- 先落库业务字段变更；
- 再更新 Diff 状态为 `adopted`；
- 任一步失败则整体回滚，避免“数据改了但 Diff 仍 pending”。

并发场景（多窗口/多人）：

- 以 `target + target_id + lifecycle_id` 做乐观锁或版本校验；
- 若状态已非 pending，再次采纳应返回幂等成功或明确冲突码，不可重复写入。
- 若前端提交的 `pending_fingerprint` 与后端当前 pending 不一致，后端应拒绝或返回冲突并附最新 pending，前端需重放。

### 8.5 前端缓存治理

- `pendingModifyDiff` / `bcd:ss:diff`（Tab 本地缓存）仅作详情桥接加速，不得作为 Diff 真实来源；口头「sessionStorage」指 **Chat Session API** 时，以消息与 `diff-reviews` 为准（见 `需求文档_sessionStorage会话与任务状态管理.md` 术语表）。
- 每次进入页面后先拉持久化状态，再决定是否恢复本地 pending；
- 若持久化状态显示 `adopted/rejected`，必须立即清空对应本地缓存。
- Tab 级缓存（如 `activeWorkbenchTabId`、`workbenchTabs`、详情页本地 diff 缓存）恢复后必须二次校验持久化状态；校验不通过时只保留 Tab 结构，不恢复旧 Diff 展示。

### 8.6 验收用例（新增）

#### 用例 P1：采纳后刷新不复现

1. 生成 Diff（pending）；
2. 采纳成功；
3. 手动刷新页面；
4. 断言：列表、详情、对话区都不再显示该 Diff。

#### 用例 P2：多次刷新不复现

1. 在 P1 基础上连续刷新 3 次并切换计划；
2. 断言：仍不复现该 Diff。

#### 用例 P3：采纳后再修改才出现

1. 在 P1 基础上再次对同记录发起新修改；
2. 断言：出现新 Diff，且 `lifecycle_id` 或 `diff_fingerprint` 与旧值不同。

#### 用例 P4：采纳后再次进入同 Tab 不复现（新增）

1. 生成 Diff 并采纳成功；
2. 关闭当前详情 Tab 或计划列表 Tab；
3. 再次进入同一计划列表/同一记录详情 Tab；
4. 断言：不出现已采纳 Diff（列表不高亮、详情无旧 diff review）。

#### 用例 P5：跨 Tab 导航后状态一致（新增）

1. 在 A Tab 触发沙箱预览，跳转到 B Tab（激活或新建）；
2. 在 B Tab 采纳 Diff；
3. 返回 A Tab，再次进入 B Tab；
4. 断言：已采纳 Diff 不复现，且不会因 Tab 切换重新注入旧 pending。

#### 用例 P6：已采纳历史沙箱预览点击跳转（新增）

1. 生成 Diff 并采纳成功；
2. 在历史消息中点击该条沙箱预览卡片；
3. 断言：可跳转到对应列表/详情 Tab（激活已有或新建）；
4. 断言：目标 Tab 中该条记录无待确认 Diff 展示。

---

## 9. 非功能要求

- 不因同步 pending 而触发意外页面跳转或自动打开详情。
- 多轮对话合并的时间复杂度应可控（按会话增量处理，避免全量重复扫描）。
- 关键操作需保留诊断日志（生成、合并、采纳、清理、恢复）。

---

## 10. 实施建议（供开发参考）

- 以 `target + target_id` 作为主键维护 pending diff map。
- 增加“生命周期版本号”或“最后修改时间戳”，明确最新 Diff 的来源。
- 合并函数保持纯函数化，输入历史事件，输出单一最新 Diff，便于测试。
- 将“列表同步 pending”与“详情打开”行为解耦（通过事件参数控制）。
- 增加 `diff_fingerprint`（建议基于规范化后的字段 old/new 计算 hash），用于跨会话去重与幂等。
- 将“采纳状态查询”封装为单独接口，页面初始化先拉该接口再恢复本地 UI。
- 增加“合并接口”契约：`pending + new -> merged`，并返回冲突码（如 `409 DIFF_CONFLICT`）支持前端重试。

## 11. 完成定义（DoD）

满足以下条件视为闭环完成：

1. 上述 4 个关键场景全部通过。
2. 列表与详情对同一记录展示一致且可复现。
3. 已采纳 Diff 在无新改动时不会再次出现。
4. 再次修改可稳定开启新一轮 Diff 生命周期。
5. 无“关闭 Tab 后自动打开详情”类副作用回归。
6. 跨会话重复生成相同 Diff 时，不会新增重复待确认项（幂等通过）。
7. 采纳后刷新页面（含多次刷新）不复现旧 Diff。
8. 沙箱预览跨计划/跨记录时，能够“激活已有 Tab 或新建目标 Tab”，且目标 Tab 语义正确。
9. 同一记录 Diff 在任意 Tab 中采纳后，重新进入该 Tab 不复现旧 Diff。
10. `grep` 导航跳转遵循与沙箱预览一致的 Tab 规则（激活已有或新建目标 Tab），且不产生错误 Tab 渲染。
11. 已采纳历史沙箱预览保留只读回看能力，但点击跳转后的目标 Tab 不出现待确认 Diff。

## 12. 操作人隔离与持久化（新增）

### 12.1 问题说明

- 沙箱预览点击后应进入与 **Diff 闭环**（见上文 §4、§10）一致的「左侧列表行内 √ / ✗」审核体验。
- 若 diff 仅含列表可展示字段，但字段标签为英文（如 `Owner`）或未映射到统一 key（`assignee`），前端会误判为「需进详情」而 `openMainEditor`，导致**左侧列表不出现行内 diff**。
- 未采纳的 Diff Review 仅**发起该次沙箱预览的操作者**可见并可采纳/拒绝；其他协作者不应看到他人待确认项。

### 12.2 数据与接口

- 表 `diff_review_state` 增加 **`operator_id`**（外键 `user.id`，可空以兼容历史行）。
- `POST .../diff-reviews/upsert`：服务端将 `operator_id` 置为**当前登录用户**，标识本条 pending 归属。
- `GET .../diff-reviews`：对 `status` 为 **`pending` / `rejected`** 的条目，仅返回 `operator_id` 为空（历史兼容）或 **`operator_id === 当前用户`** 的记录。
- `POST .../diff-reviews/resolve` 与 `POST .../modify`（确认采纳）：若目标 pending 行的 `operator_id` 已设且**不是当前用户**，返回 **403**，避免代他人采纳。

### 12.3 前端

- Diff 字段名归一化：`Owner` / `owner` / `Assignee` 等与 `assignee` / `assignee_id` 统一映射后再判断「仅列表字段」与构造 `pendingModifications`，与 **grep 导航 + 列表闭环** 使用同一套列表列（标题、状态、负责人等）。

### 12.4 完成定义（补充）

1. 仅修改负责人（英文标签）时，从沙箱跳转后**左侧列表**出现行内 old→new 与 √ / ✗，而不是只打开详情。
2. 用户 A 产生的未采纳 pending，用户 B 在同一项目下**列表/API 均不可见**且不可代为采纳。
