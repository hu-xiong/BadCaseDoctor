# 需求文档：增量总结（每步合并 Observation + SSE 实时推送）

## 1. 文档目标

定义「增量总结」能力的产品行为、触发时机、与现有 Agent ReAct / SSE 协议的衔接方式，以及前后端职责边界，作为设计与实现的依据。

---

## 2. 背景与现状

### 2.1 现状

- Agent 执行多步工具调用（THINK → ACT → OBSERVE 循环），每步会产生 **observation**（工具执行结果的可读摘要或原始结构化信息）。
- 当前面向用户的 **总结（summary）** 多为 **整轮任务结束时的最后一次总结**，用户在长任务执行过程中难以持续获得「截至目前为止」的凝练结论。

### 2.2 目标

- 每完成一个可纳入总结的步骤后，将 **本步 observation** 与 **当前已有的全局总结** 合并，调用大模型生成 **新的全局总结**。
- **新总结覆盖旧总结**（会话内维护单一「当前总结」版本，而非保留每一步一份独立总结副本，除非另有审计需求）。
- 通过 **SSE** 将每次更新后的总结 **实时推送给前端**，便于聊天区或侧栏持续刷新展示。
- 下一步 observation 到达后，重复「合并 → 生成 → 覆盖 → SSE 推送」，直至 **所有步骤结束**（或任务显式终止/失败）。

---

## 3. 范围

### 3.1 纳入范围

- 后端：在 ReAct / Agent 主循环中，在 **合适的步骤边界** 触发增量总结；调用 LLM；通过现有或扩展的 SSE 事件下发。
- 前端：消费 SSE 中的增量总结事件，更新 UI（覆盖展示、可选轻量动画/时间戳）。
- 可选：与消息落库字段对齐（若 AI 消息需持久化「当前总结」快照）。

### 3.2 不纳入范围（除非后续单独立项）

- 对历史会话自动回溯重算增量总结。
- 多用户协同编辑同一条总结。
- 离线批处理总结（与「实时 SSE」正交）。

---

## 4. 术语

| 术语 | 含义 |
|------|------|
| **步骤** | 一次工具调用从 executing 到 observation 完成的一个原子单元（或产品定义的等价边界）。 |
| **Observation** | 该步骤工具输出的、用于展示或推理的观察结果（可为文本摘要或经裁剪的结构化片段）。 |
| **当前总结** | 截至上一轮增量合并后，面向用户的全局结论文本（单字段或结构化中的 summary 字段）。 |
| **增量总结** | 在「当前总结 + 新 observation」输入下，由 LLM 重新生成的、覆盖旧值的新总结。 |

---

## 5. 功能需求

### 5.1 触发时机

1. **主路径**：某步骤 **observation 已确定**（工具成功返回或失败但已有稳定可展示的 observation 文本）后触发一次增量总结。
2. **跳过步骤**：若步骤被跳过且无有效 observation，**不触发**或按产品规则传入占位说明（需二选一并在实现中写死策略）。
3. **并发/并行**：若存在多 observation 在同一时刻就绪，应 **串行化** 对「当前总结」的更新（见 6.3），避免丢失更新或乱序覆盖。

### 5.2 输入构成（给 LLM）

每次调用至少包含：

- **当前总结**：上一轮结果；首轮可为空字符串或固定引导语（如「尚无总结」）。
- **新 observation**：本步结果（建议带 **步骤序号 / 工具名 / step_id**，便于模型区分层次）。
- **可选上下文**：用户原始问题摘要、计划标题、locale、截断策略说明。

### 5.3 输出与覆盖策略

- 模型输出 **单一新版本全文总结**（或协议约定的 JSON 字段），**完全替换**内存中的「当前总结」。
- **不向用户暴露**中间版本的多条并存（除非调试模式）；前端仅展示「当前最新」。

### 5.4 SSE 推送

1. 每次生成完成（或 **流式生成时按 chunk**，若选用流式）通过 SSE 下发。
2. 事件需携带 **版本或序号**（如 `summary_revision` 单调递增），便于前端丢弃乱序包。
3. 与现有 `step` / `done` / `finished` 等事件 **兼容**：不破坏现有解析；新增独立 `type` 或子字段扩展（实现阶段选定一种并写入协议说明）。

### 5.5 结束条件

- **正常**：所有计划步骤执行完毕，最后一次 observation 已参与合并并推送最终总结后，可与现有 `done`/`finished` 逻辑并存（最终总结可与增量最后一条一致，避免重复调用——见 7.2）。

---

## 6. 非功能需求

### 6.1 延迟与体验

- 增量总结为 **附加 LLM 调用**，应 **异步** 执行，**不得阻塞** observation 本身对前端的及时展示（可先推 observation，再推 summary_update）。
- 若用户离开页面，以服务端会话状态为准；重连后的补偿策略可选（首期可不做）。

### 6.2 成本与频控

- 每步一次调用可能成本较高；可提供 **开关**（环境变量或请求参数）：`增量总结 开/关`。
- 可选 **防抖**：同一窗口内多条小 observation 合并后再总结（本期可不做，文档保留扩展位）。

### 6.3 一致性与顺序

- 对同一 `request_id` / `session_id` 维护 **单调 revision**，合并逻辑 **单线程** 或 **队列串行**，保证「当前总结」与 observation 应用顺序一致。

### 6.4 安全与隐私

- 传入模型的 observation 遵守现有脱敏、截断、日志策略；禁止将密钥等敏感字段拼入总结 prompt。

---

## 7. 与现有实现的衔接（建议）

### 7.1 代码落点（供开发对照，非最终实现）

- ReAct 引擎在 observation 产出后：`agents/react_simplified.py` 及相关流式合并逻辑。
- SSE 封装与路由：`routers/agent.py` 的 `/api/agent/react` 流式响应。
- 前端消费：`electron-vue3` 中现有 SSE reducer / `SimpleChatPanel.vue` 或统一 composable。

### 7.2 与「最终 done 总结」的关系

| 策略 | 说明 |
|------|------|
| **A. 去重** | 若最后一步增量总结已覆盖全部 observation，则 `done` 中不再单独调用大模型生成总结，仅引用当前总结。 |
| **B. 保留双轨** | `done` 仍生成「终稿」；增量仅供过程展示。产品需接受终稿可能与倒数第二步增量略有差异。 |

**建议**：采用 **策略 A** 或 **终稿对当前总结做一次轻量润色**（单次调用），以控制总调用次数并避免用户看到两次明显矛盾的长文。

---

## 8. 验收标准

1. 多步任务执行中，每完成一步（有 observation），前端能在 **不刷新页面** 的情况下收到至少一次 **总结更新** SSE，且展示内容与该步之前相比包含新信息。
2. 刷新页面后（若已持久化），最后展示的总结与关窗前 **最终增量版本** 一致（若未做持久化，则本条仅适用于同一会话不断连场景）。
3. 快速连续多步完成时，前端不因乱序 SSE 出现 **回退到旧总结**（revision 校验生效）。
4. 关闭增量总结开关时，行为与改造前一致（仅最终总结或无总结，与现网一致）。

---

## 9. 待定事项

1. **失败步骤**的 observation 是否进入总结（如工具超时、部分错误）。
2. **流式总结** vs **整段返回**：首版建议整段返回 + 单次 SSE，降低前端复杂度。
3. **Token 上限**：当前总结 + 新 observation 超长时的截断与摘要策略。
4. **国际化**：总结输出语言与用户 `locale` 对齐规则。
