# modify 沙箱预览性能优化 — 需求与决策文档

## 1. 文档目的

供产品/研发评审 **「为什么慢」** 与 **「可接受的优化手段」**，避免将「对话里改两条 testcase 负责人」误解为「生产库一条 UPDATE ≈ 30ms」。  
**实现级拆解、环境变量速查**见同目录：`需求文档_modify耗时分析与优化_20260330.md`（下文称《耗时分析》）。

---

## 2. 一、核心问题确认

### 2.1 瓶颈

- **位置**：`sandbox_executor._prepare_db_copy` 内对 SQLite 使用 **`shutil.copy2` 复制整个数据库文件**到临时路径（见 `agents/tools/text2sql/sandbox_executor.py`）。
- **后果**：**拷贝耗时与 `.db` 文件大小近似线性相关**；几 GB 的测试库，单次拷贝就可能 **数秒～十几秒**，这往往是界面上 **「~20 秒」** 的主要来源。
- **误解**：多数人以为慢在「执行几条 UPDATE」；实际上是 **安全隔离（整库可写副本）** 的代价，不是单条 SQL 的执行时间。

### 2.2 与「批量预览」的关系（对齐当前实现）

- **主路径（推荐）**：`_preview_in_sandbox_batch`（`MODIFY_SANDBOX_DIRECT_SQL=1` 时）已是 **「一次整库副本 + 在该副本上 `executescript` 多条 UPDATE」**，**不是**「每行记录各拷贝一整库一次」。
- **仍会多次整库拷贝的情况**：连续多次 **单条** `_preview_in_sandbox`（每条通常 `_prepare_db_copy` 一次）。  
- **已实现（批量）**：`executescript` 失败时**复用同一份副本**逐条 `execute`，不再为回退路径重复 `copy2`；若仍失败再删除副本（仍不碰生产库）。

### 2.3 端到端在做什么（摘要）

| 序号 | 环节 | 量级直觉 | 说明 |
|------|------|----------|------|
| A | ORM 批量读行 | 通常 ms～百 ms | `_fetch_original_rows_batch_orm` 等 |
| B | 预览增强与 diff | 与行数、字段有关 | `_enrich_modified_data_for_preview`、`_generate_line_diff` |
| C | **整库文件副本** | **与 DB 文件大小强相关** | **`shutil.copy2` 整文件** |
| D | 副本上执行预览 SQL | 通常 ms 级 | 批量为 `executescript` 多语句 |
| E | 清理临时文件 | 通常 ms 级 | 删除临时副本 |

modify 在 ReAct 中经 **线程池**执行；日志里「已等待 Xs」反映的是 **工具未返回** 的墙钟，不等价于「纯 SQL 耗时」。

## 3. 二、优化方案（按推荐顺序与收益）

以下 **P0 / P1 / P2** 与实现成本、风险一并列出，可按风险承受能力裁剪。

### P0（优先落地，整体低风险）

#### P0-1：临时副本放到高速介质（tmpfs / 内存盘 /  fast TEMP）

- **思路**：将沙箱副本目录置于 **内存文件系统** 或 **高性能本地盘**，缩短 `copy2` 墙钟。
- **Linux**：`db_copy_dir` 或 `tempfile.mkdtemp(dir='/dev/shm')`（需保证容量和可写；容器内注意 `/dev/shm` 大小）。
- **Windows**：无 `/dev/shm`；可用 **RAM 盘**、或将 `TEMP` / 配置的 **`db_copy_dir`** 指到 **NVMe SSD**；可通过环境变量统一副本父目录，无需写死路径。
- **收益**：在机械盘或冷盘上，拷贝可下降 **一个数量级** 量级（具体依内存带宽与库大小而定）；「降低 90%」仅在 **对比极慢源盘 vs 内存** 场景下可能成立，需以 **分段计时** 实测。
- **风险**：tmpfs 占用 **RAM**，副本 **用完应删**（现有逻辑会删临时文件）；大库 + 并发预览需控制内存上限。

#### P0-2：批量预览坚持「单次拷贝」（治理回退路径）

- **现状**：批量主路径已 **单次拷贝 + 批量 SQL**；优化重点是 **减少回退**（失败原因日志、`MODIFY_SANDBOX_DIRECT_SQL` 保持开启、避免无谓逐条路径）。
- **若历史代码或分支仍存在「逐条预览、每条拷贝」**：应合并为 **一次拷贝 + 多条 UPDATE**，与当前 `_preview_in_sandbox_batch` 对齐。
- **收益**：避免 **N × copy_time**（回退场景）。
- **风险**：需兼容失败重试与前端 `batch_preview_row` 顺序；数据结构可尽量复用。

#### P0-3：SQLite **backup** 仅复制必要表（替代整文件 copy2）

- **思路**：用 `sqlite3` **backup**（或按表导出/导入）在 **临时库** 中仅包含 **testcase / badcase / bug** 及 **依赖表（如 user）**，再在该库上执行预览 UPDATE。
- **收益**：拷贝数据量显著下降，大库场景优于整文件 `copy2`。
- **复杂度**：中等；需梳理 **外键与触发器**、保证预览 UPDATE 与真实库语义足够一致。
- **注意**：只读连接无法在原地做「执行后 ROLLBACK」跨连接写预览；**可写隔离**仍应在副本/子库上完成。

### P1（需改造，收益显著）

#### P1-1：ORM 已读行 + diff 后，**可选跳过沙箱执行**（或仅轻量校验）

- **思路**：`confirm=False` 且修改模式可证明 **仅展示 diff、不依赖副本上真实执行** 时：**ORM 读行 + 内存/规则生成 after + diff** 已完成主要价值；**整库拷贝 + executescript** 仅在「必须验证 SQL 可执行 / 约束」时启用。
- **开关建议**：在已有 `MODIFY_ORIGINAL_DATA_ORM_FIRST` 等之上，可增加如 **`MODIFY_SANDBOX_SKIP_IF_POSSIBLE`**（命名待定），分支内严格白名单（字段、语句形态）。
- **收益**：预览阶段可 **砍掉整段 copy2**，Often **秒级 → 亚秒级**（视 ORM/diff 而定）。
- **风险**：需产品接受「部分场景仅逻辑 diff、不在副本执行」；可提供 **强制校验** 子模式。

#### P1-2：`:memory:` SQLite + backup 导入子集

- **思路**：`sqlite3.connect(":memory:")`，再 backup **必要表** 至内存库，执行预览，丢弃。
- **收益**：减少磁盘 I/O；适合 **中等规模库**。
- **限制**：库过大时受 **可用内存** 约束，需上限与回退（仍用文件副本）。

### P2（长期 / 架构）

#### P2-1：**异步预览** + SSE 推送结果

- 前端先进入「预览生成中」，后台任务结束后推送 **observation** / 预览包。  
- 需 **状态机、任务 ID、取消** 等设计。

#### P2-2：**Server 端事务 ROLLBACK 预览**（非当前 SQLite 单体模式）

- 若未来为 **PostgreSQL / MySQL** 等：可在 **独立事务** 中执行 UPDATE 后 **ROLLBACK**，无需整库文件拷贝。  
- **与当前以 SQLite 文件为主** 的部署需单独评估迁移成本。

## 4. 三、立即可以动手的优化（最低成本）

1. **副本目录指向高速盘或 tmpfs（Linux）**  
   - **环境变量 `SANDBOX_DB_COPY_DIR`**：沙箱 SQLite 副本父目录（已接入 `SecurityConfig.db_copy_dir` 默认逻辑及 `_prepare_db_copy`）。未设置时默认为 **`%TEMP%/badcase_sandbox_db_copy`（Windows）或系统临时目录下同名字目录**。  
   - Linux 可指向 `/dev/shm/...` 等；Windows 可指向 **NVMe 路径**或 **RAM 盘**；Docker 需保证目录可写且容量足够。

2. **默认保证 ORM 优先读行**  
   - 保持 `MODIFY_ORIGINAL_DATA_ORM_FIRST=1` 等口径；与 **「跳过沙箱执行」开关**（P1-1）联调时再收敛分支。

3. **分段耗时打点**  
   - 在 `_prepare_db_copy` 前后输出 **`copy_ms`**；在 `_preview_in_sandbox_batch` 内输出 **`exec_ms`**（及回退次数）。  
   - 配合 `PERF_LOG=1` 或写入 observation 可选字段，便于确认 **拷贝占比** 与优化效果。

## 5. 四、安全边界提醒

- **绝不能**为追求速度 **默认**把预览写直接打在 **生产库** 上。  
- 所有「轻量沙箱」「子集 backup」「跳过副本执行」等方案，必须在需求中写清：  
  - **默认行为**、  
  - **开关与白名单**、  
  - **误写防护与审计**。  
- **仅复制部分表**时，需评估 **外键与一致性**；测试库通常风险可控，但仍需在文档与用例中列回归项。

## 6. 五、总结与优先级建议

| 优先级 | 动作 | 预期方向 |
|--------|------|----------|
| 1 | 副本放到 tmpfs / 快盘 + 分段计时验证 | 大库下 **`copy_ms` 显著下降** |
| 2 | 消除批量 **回退逐条**、保证单次拷贝主路径 | 避免 **N × 复制** |
| 3 | ORM+diff 与 **可配置跳过沙箱执行** | 预览接近 **秒级 / 亚秒级**（受 diff 与规则限制） |
| 4 | 子集 backup / `:memory:` | 中长期降低 **拷贝字节数** |

**预期管理**：在 **GB 级整库 copy2** 未优化前，**20s 级** 主要来自拷贝而非 SQL；完成 **1+2** 后常见部署可望降到 **数秒级**；再配合 **3** 在允许的产品边界下逼近 **秒级**（依库大小与是否仍执行副本校验而定）。**不承诺**全场景 30ms。

## 6.1 三模式配置（已实现）

| 模式 | 描述 | 安全等级 | 速度 | 实现复杂度 |
|------|------|----------|------|------------|
| 全库拷贝 `full_copy` | 最安全，副本上完整写验证 | ⭐⭐⭐⭐⭐ | ⭐ | 已完成 |
| 轻量子集库 `subset`（默认） | 只抽取目标表+目标行到临时库，再做写验证（仍隔离） | ⭐⭐⭐⭐ | ⭐⭐⭐ | 中 |
| 跳过写验证 `skip_update` | 仅 ORM+diff 预览，不执行沙箱 UPDATE | ⭐⭐ | ⭐⭐⭐⭐⭐ | 低 |

统一开关：`MODIFY_SANDBOX_PREVIEW_MODE=full_copy|subset|skip_update`（未设置时默认 `subset`）\n
