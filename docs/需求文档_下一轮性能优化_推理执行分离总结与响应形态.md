## 2. 总体目标（量化）

| 指标 | 现状（参考） | 目标 |
|------|----------------|------|
| **简单任务端到端推理主导路径** | 约 **9.5s** 量级（以「grep + modify」等短链路、少轮次任务为样本；精确口径在实现阶段用同一批基准用例 + `PERF_LOG` 固化） | **≤ 3s**（同口径） |

说明：**简单任务**指：意图清晰、工具链可预测（典型为 **grep → modify** 或单工具）、无需多轮复杂探索与长上下文分支的任务。复杂任务可另设指标，不强制纳入本条 3s 承诺。

## 3. 需求一：推理与执行分离（核心）

### 3.1 问题陈述

当前主循环在「工具结果已出」之后，仍可能经历 **观察（observe）→ 与决策相关的 UI/解析 → 再进入下一轮思考（decide）** 等路径；对 **已在推理阶段明确产出「grep + modify」组合计划」** 的场景，这属于重复认知：**执行阶段不应再次完整走「观察—思考—决策」来决定下一步**，否则带来额外 LLM 调用与串行等待，与简单任务 3s 目标冲突。

### 3.2 目标行为（产品语义）

1. **推理阶段（Think / Plan / Decide 的一次性产出）**  
   在判定为「简单 grep-modify 闭环」或等价路由命中时，模型或规则层应一次性产出 **可执行的宏步骤**：  
   - 已确定的 **grep** 参数意图（或可机械校验的结构）；  
   - 已确定的 **modify** 参数意图（在 grep 结果约束下的替换/编辑策略）；  
   或产出 **「一轮」内** 工具序列的冻结计划（至少覆盖 grep + modify）。

2. **执行阶段（Act）**  
   - **只做**：参数/schema 校验、路径与安全策略校验、配额与并发限制、工具执行与错误归一。  
   - **不做**：为决定「下一步用哪个工具」而再调用一次完整 **observe LLM**；不做「执行中途再开一轮 decide」来选工具（除非执行失败且进入 **3.4** 的恢复策略）。

3. **一轮闭环定义**  
   **一轮** = 推理已输出的 **grep + modify**（或等价序列）在**无中途再决策**的前提下 **顺序执行完毕**，或 **中途报错终止**，或 **业务规则判定需升级复杂度**（见 3.4）。

4. **何时进入下一轮循环**  
   仅当：  
   - **整轮执行完成**（grep 与 modify 均成功且状态一致）；或  
   - **整轮内任一步失败**（参数错误、工具异常、沙箱拒绝等）；或  
   - **命中升级条件**（见 3.4）。  

   进入下一轮时，才重新允许 **完整的观察 / 思考 / 决策**（或按 5 节的新响应形态走 FC + 文本协议）。

### 3.3 与现有 ReAct 循环的关系

- **兼容**：保留全局安全与日志、SSE 事件序列对前端的可理解性（可在事件名不变前提下压缩内部阶段）。  
- **变更**：在「宏计划已冻结」分支内，**缩短或跳过** `ReAct_观察结束到下一轮思考_间隙说明.md` 中标注的 **observe / 增量总结 / 并行 UI 总结** 等可对简单路径关闭或降级的子步骤；**不得**在宏执行中途默认再触发一次「为选工具服务」的 decide。  
- **实现落点（实现阶段细化）**：`agents/react_simplified.py` 主循环、grep/modify 路由与 `agents/tools/modify_tool.py` 等调用边界；需定义明确的状态机字段（例如 `frozen_macro`、`macro_round_id`）。

### 3.4 失败与降级（必选）

| 场景 | 行为 |
|------|------|
| grep 失败或结果为空且计划依赖命中 | 允许进入 **恢复轮**：完整思考/观察或缩小范围重试；需有次数上限与对用户可见说明。 |
| modify 预览/应用失败 | 同上；可携带 grep 快照作为上下文，避免从零推理。 |
| 模型输出宏计划不完整或校验不通过 | 不执行半套工具；回退到现有「逐步决策」路径，并打点监控。 |

### 3.5 验收标准（本条）

1. 基准用例集（grep+modify 简单修复类）下，**P50 端到端 ≤ 3s**（网络与模型供应商波动可单独记录分位）。  
2. 在宏计划路径上，**grep 与 modify 之间**不出现「完整 observe LLM + 新一轮 decide」的默认组合（可用日志关键字或 `PERF_LOG` 断言）。  
3. 失败用例仍能回退到安全、可解释路径，无静默跳过错误。

## 4. 需求二：总结耗时优化（约 2s 可挖空间）

### 4.1 背景

当前在 **每步 observation 之后** 往往还存在 **增量总结 / 决策说明 UI 流 / 解析与 phase_wait** 等链路；其中 **增量总结默认开启** 时，会额外引入 **一次（或多次合并）静默 LLM 调用**，与主路径串行叠加，用户体感常为 **~2s 级** 或更高（与模型、payload、是否流式有关）。

### 4.2 耗时可能分布（假设与验证方法）

以下需在下一轮用 **同一 `request_id` 的 `PERF_LOG` 分段埋点** 验证占比，本文先列**可疑大头**与**节省思路**。

| 环节 | 可能耗时来源 | 节省方向（设计层） |
|------|----------------|---------------------|
| **增量总结 LLM** | 每步合并「当前总结 + 新 observation」的全文生成 | **简单任务/宏路径关闭**或改为 **异步**（不阻塞进入下一轮或宏执行）；或 **降频**（仅关键步骤、仅失败步骤、仅最后一跳）。 |
| **observe LLM** | grep 常走完整 observe（见 ReAct 间隙说明） | 宏路径下 **跳过**；非宏路径保留或缩短 `max_tokens`。 |
| **decision_observe / UI 总结 LLM** | 与 observe 并行仍可能触发 `ui_observe_summary` 等 | 简单路径 **模板化** 或 **summary_nl 分块** 已足则 **禁止二次 LLM**；统一开关收口。 |
| **解析与合并** | `parse_xml_findings`、grep 列表兜底合并 | 大文本时裁剪输入；本地解析保持 O(n) 可接受。 |
| **串行相位** | `phase_wait`、round 切换前后清理 | 宏路径合并 UI 态；减少无用户价值的等待节点。 |

### 4.3 目标与约束

- **目标**：在「简单任务」样本上，总结相关链路相对现状 **再省约 2s**（与 3 节目标一并验收；可分项：仅总结子项 P50 下降 ≥2s 或总链路下降 ≥2s，实现阶段二选一写死）。  
- **约束**：  
  - 关闭或异步总结时，**不得**破坏最终可交付的「用户可见结论」——至少任务结束或显式节点处有一次可靠总结或等价展示。  
  - 异步总结若乱序到达，需 **revision** 丢弃旧包（与现有增量总结文档一致）。

### 4.4 验收建议

- 基线/优化后对比：**总结相关 LLM 调用次数、总耗时、与 observation 的串行重叠时间**。  
- 前端：聊天区/侧栏总结仍连贯，无明显闪烁回退（除非新版本 revision 合法覆盖）。

## 5. 需求三：response_format 与 Function Calling 结合（框架）

### 5.1 背景

当前协议侧大量依赖 **三段式 XML**（例如思考/观察/决策等分段），对模型遵循与前后端解析友好；同时系统已部分使用 **Function Calling（FC）** 承载工具选择与参数结构化。

**矛盾点**：纯 XML 在长链路下 **解析成本高、易混入自然语言**；纯 FC 又 **不擅长承载长推理叙述与产品化分段展示**。

### 5.2 目标形态（原则）

1. **保留** 面向用户与审计的 **XML 三段式（或等价分段）** 作为 **叙事与中间结论** 的载体（可继续流式）。  
2. **引入/强化 FC** 作为 **机器可读、强 schema** 的载体，用于：  
   - 工具名与参数；  
   - **宏计划**（见第 3 节）的冻结结构；  
   - 与 `response_format`（若供应商支持）结合的 **结构化字段**，减少「从 XML 抠 JSON」的失败率。  
3. **一次响应中允许「XML 叙事 + FC 工具调用」并存**：由后端定义 **优先级与合并规则**（例如：同轮内 FC 为准，XML 仅展示；或 XML 内嵌占位符引用 `call_id`）。

## 6. 非功能需求（节选）

- **可观测**：宏路径命中/回退次数、各段 `PERF_LOG`、FC 解析失败率。  
- **安全**：宏执行路径不得绕过现有路径校验与沙箱策略。  
- **回滚**：环境变量或功能开关一键回到「逐步 observe + decide」旧路径。
