# 需求2：编辑改动 Diff 视图与采纳流程（Bug / Badcase / Testcase）

**状态**：待办  
**优先级**：高  
**创建日期**：2026-03-11

---

## 背景 / 问题

- 当前通过对话面板驱动“修改 bug / badcase / testcase”时，改动展示不够清晰：缺少逐字段 diff、采纳/拒绝的统一交互，以及采纳后的回放/定位与预览联动。
- 现有 diff 视图观感较差；输入框/文本域希望达到 Cursor 类工具的“文本在区域内直接显示 diff”的效果，而不是把 diff 文本放在上方。
- 需要像桌面软件那样把每个 badcase/bug/testcase 视作“文件”，拥有**文件属性描述（元数据）**与**改动记录**，以便审计、回溯、以及多轮对话持续编辑。

## 需求描述

### 1) 统一的改动模型（把实体当成“文件”）

- **实体即文件**：每个 `badcase`、`bug`、`testcase` 被视为一个“文件对象”。
- **文件属性描述（元数据）**至少包含：
  - `file_type`: badcase / bug / testcase
  - `file_id`: 对应实体 id
  - `title/name`: 展示名
  - `version/revision`: 当前版本号（或更新时间戳）
  - `last_modified_at`、`last_modified_by`（用户/会话/租户维度）
- **改动记录（diff/patch）**：记录每次通过对话触发的“提议修改”，并可逐字段采纳/拒绝。

> 存储位置取舍（建议）：  
> - **云端（后端 DB）存储为主**：跨设备/多租户一致、可审计、对话可追溯；桌面端仅做缓存。  
> - 本地存储仅作为离线缓存或性能优化，不作为唯一事实来源。

### 2) 两类编辑场景与展示位置

#### A. 列表级快速编辑（只改列表中的三个属性）

- 当通过对话面板触发修改，且仅涉及“列表上展示的三个属性”时：
  - **diff 展示在列表行内**（不进入详情页也能看出改动）。
  - 每个字段旁提供 **对号（采纳）** 与 **X（拒绝）**，交互沿用你现有逻辑。
  - 采纳/拒绝后，列表立即刷新到最终值，且该字段不再显示 diff。

#### B. 详情级字段编辑（改详情里的任意字段）

- 当通过对话面板触发修改，且涉及详情字段：
  - 在详情页中，对**每一个发生改动的字段**显示 diff（逐字段）。
  - 每个字段 diff 都有 **对号/ X**（采纳/拒绝）。
  - **一个详情 = 一个沙箱预览**：本轮详情修改的预览来自同一次沙箱执行/预览结果（聚合显示），避免每个字段各跑一次沙箱。

### 3) Diff 视图交互与视觉要求（Cursor 风格）

- **文本框/文本域内呈现 diff**：
  - “删除的文字”在文本区域内以 **暗红色**（例如背景或前景）标识（且可读，不刺眼）。
  - “增加的文字”在文本区域内以 **暗绿色** 标识。
  - 不要把 diff 文本堆到输入框上方，而是把差异直接渲染在文本区域的内容层里（类似编辑器/IDE 的 diff 体验）。
- **逐字段 diff 形态**：
  - 短文本（input）：支持字符级或词级高亮。
  - 长文本（textarea/markdown）：支持行级 diff + 行内高亮（至少要有行级）。
- **采纳后的回放**：
  - 用户点“采纳”后，系统再次从沙箱预览回到原位置（保持滚动/定位），但该字段已落库/落状态后 **不再显示 diff**（展示为最终文本）。

### 4) 处理逻辑完善（提议 → 预览 → 逐字段采纳/拒绝 → 落地）

- **提议修改**：对话返回的修改建议要结构化为“字段级 patch”：
  - `path`：字段路径（如 `detail.steps[2].expected`）
  - `old_value` / `new_value`
  - `diff`：可选（前端也可生成），但建议后端也能生成以便一致性
  - `status`：proposed / accepted / rejected
- **沙箱预览**：
  - 详情编辑时，“本轮提议集合”生成一次预览（一个详情一个预览）。
  - 预览结果要能映射回具体字段（至少能回到详情页同一位置）。
- **采纳/拒绝**：
  - 字段级操作：只影响该字段 patch。
  - 当全部字段 patch 都被处理（accepted/rejected），本轮编辑会话结束并写入改动记录。

### 5) 推理步骤与 diff 的关系（对齐你提到的 Cursor/IDE 思路）

- IDE 的文件 diff 本质上是“文件内容 + 版本 + patch（差异集）”。
- 在本项目里可对应为：
  - “文件内容” = badcase/bug/testcase 的当前详情 JSON（或表结构映射后的视图）
  - “版本” = revision / updated_at
  - “patch” = 字段级改动列表（可序列化存储）
- 这样可以支持：
  - 多轮对话连续编辑（在同一 revision 基础上叠加 patch）
  - 审计（谁在何时提议了什么、采纳了什么）
  - 回滚/重做（后续需求可扩展）

## 约束规则

- 保持与现有“列表三个属性编辑”的对号/X 逻辑一致（不破坏旧流程）。
- 详情字段改动必须逐字段可采纳/拒绝，并能定位回原位置。
- Diff 视图需升级为更美观、更接近 Cursor 风格的“文本区域内 diff”。

## 验收标准

- [ ] 通过对话面板修改 `badcase/bug/testcase`：
  - [ ] 若仅修改列表中的三个属性：diff 直接在列表上展示；对号/X 也在列表上；交互延续旧逻辑。
  - [ ] 若修改详情字段：详情页每个被改动字段都有 diff + 对号/X；并且 **一个详情对应一次沙箱预览**（聚合预览）。
- [ ] 采纳某字段后，再次从沙箱预览回到该字段所在位置（滚动/定位正确），且该字段不再显示 diff（只显示最终值）。
- [ ] Diff 颜色规范：删除为暗红、增加为暗绿，且渲染在文本区域内部（非上方堆叠）。
- [ ] UI 观感较现状明显改善（输入框/文本域的 diff 样式更接近 Cursor/IDE）。

## 备注

- 本需求只定义“逐字段 diff + 采纳/拒绝 + 预览联动 + 变更记录模型”；具体后端表结构、前端组件实现可在实现阶段细化。
