## 三、E2E Grep project=1（真实 ES）

### 3.1 keywords=登录（2字）→ bm25_only
- total ≈ 79 ms
- query_embed = 0
- es_hybrid_search ≈ 79 ms
- 召回 1 条 badcase（标题「问登录问题答的不好」）

### 3.2 整句 32 字 → hybrid（Config 用 plus 1152 维 query）
- query_embed ≈ 858 ms（首次）
- ES 报错: query vector 1152 维 ≠ 索引向量 1024 维
- hybrid KNN 失败，回落 SQL，列表为空

### 3.3 同句第二次（进程内 embedding 缓存）
- query_embed ≈ 0 ms（缓存命中）
- ES 仍维度不匹配，total ≈ 158 ms

## 四、选型结论（测试驱动）

1. **阈值 8/80：保持** — 与预期一致。

2. **模型必须与 ES 索引维度一致（当前索引=1024）**
   - Config 默认 plus → query 1152 → **hybrid 向量检索不可用**
   - 与「数据按 Qwen 建库」一致时，索引更像 **text-embedding-v3/v4 或 qwen2.5-vl（1024）**

3. **若暂不重建索引（推荐先修生产）**
   - GREP_EMBEDDING_MODEL=text-embedding-v3（或确认建库用的确切模型）
   - 预期 hybrid: embed ~270ms + ES ~330ms ≈ **0.6s**

4. **若坚持用 vision-plus-2026-03-06（1152）**
   - 必须 **全量 re-embed + 新物理索引**，否则 hybrid 只有 BM25 或走 SQL 回落

5. **flash（768）/ v1（1536）/ qwen3-vl（2560）** 均与当前 1024 索引不兼容

6. **最快且需换库**: text-embedding-v1 ~193ms 但 dims=1536，仍要重建索引

## 五、建议 .env（对齐 1024 索引 + 8 字阈值）

GREP_EMBEDDING_BACKEND=dashscope
GREP_EMBEDDING_MODEL=text-embedding-v3
GREP_QUERY_EMBED_MIN_CHARS=8
GREP_QUERY_FULL_VECTOR_MIN_CHARS=80
